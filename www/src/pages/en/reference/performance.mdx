## Compiled Formatter

Every item returned by `get`, `query`, `scan`, and `parse` is shaped by ElectroDB's formatter: it applies getters, unwraps sets, walks nested maps/lists, filters to requested attributes, and enforces ownership. By default this runs through an interpreted path that re-walks the schema for every item.

When enabled, ElectroDB JIT-compiles a formatter specialized to a single entity's schema and uses it in place of the interpreted path, reducing per-item overhead on reads. Output is identical; only the formatting cost changes.

This is **opt-in** and **off by default**.

### How much it helps

Formatting cost scales roughly with `items × attributes` per response, so the win grows with page size:

- **Large pages** (thousands of items) — the biggest gains: roughly 15–20% less CPU per request, enough to nearly close the gap between ElectroDB and a raw DocumentClient.
- **Small pages** (tens of items) — a smaller share of the win (~10% less CPU per request), since fixed per-request cost dominates over per-item formatting.

Reads that return a single item or a handful see little difference. Actual numbers depend on your schema (attribute count, nesting, sets); the shape — bigger pages, bigger payoff — holds.

### Enable per entity

```typescript
const entity = new Entity(schema, { table, client, compile: true });
```

The formatter is compiled once, when the `Entity` is constructed.

### When it is skipped

Compilation falls back to the interpreted path (unchanged behavior) when:

- The schema defines any user getter on an attribute. Custom getters run arbitrary code, so those schemas are never compiled.
- Runtime code generation is unavailable (`new Function` is blocked, e.g. under a strict CSP).

### Services

`ServiceConfiguration` also accepts `compile`. It applies to member entities joined as raw models; it is a no-op for pre-built `Entity` instances, which carry their own `compile` setting.
